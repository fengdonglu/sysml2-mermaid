# 设计背景

[English](BACKGROUND.md) | 中文

本文记录本项目路线背后的推理，提炼自早先关于"如何做最轻量的 SysML v2 渲染器"的探讨。原始对话保留在本地（gitignore 的 `reference/` 目录）以备溯源。

## 核心思想：文本即真相源

SysML v2 定义了一套抽象语义模型；`.sysml` 文本与任何图表都是它的两种表示。对轻量工具包而言，务实的立场是：

- **`.sysml` 文本是唯一真相源。**
- **图表是实时投影**——由文本重新计算，绝不持久化。
- **不持久化布局、不要求图形编辑。** 这避开了经典的"双真相源"问题（模型与视图/布局文件互相漂移），正如 IDE 从源码渲染类图却不保存节点坐标。

## 为什么用 Mermaid

Mermaid 已提供渲染管线的后半段：节点/边图模型（`Node`、`Edge`、`Cluster`）与布局引擎（dagre，以及 ELK 集成）。SysML 工具可复用它，把精力放在前半段——理解 `.sysml` 文本并投影为图。

## 图类型难度排序

并非所有 SysML 视图等价，大致是：

- **容易（节点/连线）**：块定义图（BDD）、需求图、状态机、活动/泳道图。它们贴合 Mermaid 的通用图模型与现有布局，泳道可用 subgraph 表达。
- **困难**：内部块图（IBD）与参数图。它们需要端口摆放、绑定连接器与约束布局——超出通用节点/连线引擎的能力，需要专门的布局（例如带端口约束的 ELK）。

因此 MVP 从容易的视图做起，把 IBD/参数图作为后置的独立部分。

## 编辑器在哪里

语言服务器（诊断、补全、悬浮、大纲）位于渲染器**旁边**——它消费同一个解析器与模型，不属于渲染管线，但决定了写 `.sysml` 是否顺手。VS Code 扩展同理：语言服务器 + 语法高亮 + 预览命令。

## 需要记住的 SysML v2 特性

- 标准栈是 **KerML**（语义内核）、**SysML v2**（语言）、**Systems Modeling API & Services**（仓库/CRUD/交换）。
- SysML v2 远比流程图语言宽广：行为、需求、参数约束、分配、视点都重要。v1 必须刻意只覆盖一个有文档的子集，而非声称完全符合。
- 语言自带 `view` / `viewpoint` 概念，是挂接"这张图显示哪些元素"的天然位置。

## 与 OPM/OPL 的关系

姊妹项目 `mermaid-opm`（ISO 19450 OPM/OPL）已在小尺度上实践了完全相同的路线，是本仓库架构、工具链与约定的工作参考。OPM 是很好的热身，因为它的节点词汇（对象、过程、状态）很小；而 SysML v2 的词汇大得多，这也是本项目视图层分量更重的原因。
