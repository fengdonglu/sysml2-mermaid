# Design: v0.2 — Requirement view and Internal Block Diagram (IBD)

English only (specs follow the sibling `mermaid-opm` convention).

## Status

- Approved for implementation planning.
- Builds on the v0.1 BDD slice (`2026-09-24-bdd-slice-design.md`). Reuses the
  `core → views → layout → render → entry points` pipeline unchanged; adds two
  views, parser constructs, and a port-aware layout for IBD.

## 1. Scope

Two features, implemented on top of the existing pipeline:

1. **Requirement diagram view** — `requirement def` / `requirement` usages,
   nesting (containment), `satisfy`, `verify`, and `dependency`.
2. **Internal Block Diagram (IBD)** — part usages with ports and `connect` /
   `interface` / `bind` connectors, including nested feature-chain endpoints.

### Explicitly out of scope

- `derive` / `trace` / `refine` / `copy` (not SysML v2 keywords; only
  `#derivation connection` metadata or plain `dependency` express them).
- `verification def` / `objective` (only bare `verify <ref>;` is parsed).
- `connection def` / `end` features, `allocation`, conjugated ports `~T`,
  port end multiplicities, `NaryConnectorPart` `(a, b, c)`.
- ELK layout; IBD uses dagre plus explicit port anchoring (ELK deferred).
- Requirement subject expressions (`subject = path`); only `subject name : Type;`
  is supported.

## 2. Parser additions

All verified against the SysML v2 textual BNF and training examples.

### 2.1 Requirements

```sysml
requirement def <'1'> VehicleMassLimitationRequirement :> Base {
    doc /* The total mass of a vehicle shall be less than or equal to ... */
    subject vehicle : Vehicle;
    attribute redefines massActual = vehicle.dryMass;
    assume constraint { vehicle.fuelMass > 0[kg] }
    require constraint { massActual <= massReqd }
    require fuelLimit;                  // reference form
    requirement ChildRequirement;        // nested (contain)
}

requirement <'UR1.1'> Load : FunctionalRequirementCheck {
    requirement Passengers;
}
```

- **Short name** (`<'1'>`) precedes the declared name and is the requirement id;
  stored as `Element.shortName`.
- `subject name : Type;` → child element of kind `subject`.
- `require` / `assume` statements → child elements of kind `constraint`; the raw
  statement text (normalized) is stored in `typeRef`; a reference form
  (`require refName;`) stores the reference.
- `doc /* ... */` sets `Element.doc` (the requirement text).
- Nesting a `requirement` inside another is **containment** (section 3).

### 2.2 Satisfy / verify

```sysml
satisfy vehicleSpecification by vehicle_design;        // assert is optional
assert satisfy engineSpecification by vehicle_design.engine_v1;
assert not satisfy req1 by q;                          // parsed, flagged negated
verify vehicleMassRequirement;
```

- `[assert] [not] satisfy <req> by <usage>;` → relationship `satisfy`,
  `sourceRef = <req>`, `targetRef = <usage>`; `not` sets `Relationship.negated`.
- `verify <req>;` → relationship `verify`, source = the enclosing element,
  target = `<req>`.

### 2.3 Ports and connectors (IBD)

```sysml
part def FuelTankAssembly {
    port fuelTankPort : FuelOutPort;
}
part def Engine {
    port engineFuelPort : FuelInPort;
}
part def Vehicle {
    part tankAssy : FuelTankAssembly;
    part eng : Engine;
    connect tankAssy.fuelTankPort to eng.engineFuelPort;      // binary connect
    interface : FuelInterface connect tankAssy.fuelTankPort to eng.engineFuelPort;
    bind tankAssy.fuelTankPort = eng.engineFuelPort;
}
```

- Ports already parse as `port name : Type;`. (Direction prefixes such as
  `in item x : T;` occur inside `port def` / `connection def`; those bodies are
  out of scope and are reported as unsupported.)
- `connect <chain> to <chain>;` → relationship `connect`, `connector = 'connect'`.
- `interface [name] [: Type] connect <chain> to <chain>;` and
  `interface <chain> to <chain>;` → relationship `connect`, `connector = 'interface'`.
- `bind <chain> = <chain>;` → relationship `bind`, `connector = 'bind'`.
- A **feature chain** is a `.`-separated list of names (`a.b.c`); it is parsed by
  `parseFeatureChain()` and stored verbatim in `sourceRef` / `targetRef`. (The
  endpoint resolver in the IBD view, section 4, splits it.)

### 2.4 Lexical additions

- `<` and `>` become punctuation tokens (for short names `<'id'>`).
- `.` already tokenizes (used by feature chains).

## 3. Model additions

`src/core/model/types.ts`:

```ts
export type ElementKind =
  | 'package' | 'import'
  | 'part-def' | 'part'
  | 'attribute-def' | 'attribute'
  | 'port-def' | 'port'
  | 'enum-def' | 'enum-literal'
  | 'requirement-def' | 'requirement'
  | 'subject' | 'constraint'
  | 'unresolved';

export interface Element {
  // ...existing fields...
  shortName?: string;         // `<'id'>`
}

export type RelationshipKind =
  | 'specialization' | 'subset' | 'redefine' | 'dependency'
  | 'satisfy' | 'verify'
  | 'connect' | 'bind';

export interface Relationship {
  id: string;
  kind: RelationshipKind;
  sourceRef: string;
  targetRef: string;
  sourceId?: string;
  targetId?: string;
  position: Position;
  connector?: 'connect' | 'interface' | 'bind';   // for connect relationships
  negated?: boolean;                              // `assert not satisfy`
}
```

**Containment edges** (parent requirement → child requirement) are derived by
the view from `ownerId`, not stored as relationships. **Allocation** is out of
scope.

`validate` gains resolution for the new relationship kinds:

- `satisfy` / `verify`: resolve `sourceRef` / `targetRef` with the existing
  qualified/simple-name rules.
- `connect` / `bind`: endpoints are feature chains (`a.b.c`). `validate` leaves
  these relationships unresolved (no placeholder, no warning); the **IBD view**
  resolves each chain to an owning part plus a port (section 4.2).

## 4. Views

`ViewName` becomes `'bdd' | 'requirement' | 'ibd'`; `selectView` dispatches.

### 4.1 Requirement view (`src/views/requirement.ts`)

**Nodes** — every `requirement-def`, `requirement`, and any element referenced by
a `satisfy` / `verify` / `dependency` edge (implementing parts, verification
cases), plus `«unresolved»` placeholders.

- stereotype: `requirement` for requirements; `block` for part-like targets;
  `unresolved` for placeholders.
- rows: `Id: <shortName>` when present; `subject: <name> : <Type>`;
  one row per `constraint` child (`require ...` / `assume ...`).
- note: `Element.doc`.

**Edges**

| Fact | Kind | Notation |
|---|---|---|
| requirement owns child requirement | `contain` | line from parent to child, open arrow |
| `satisfy R by X` | `satisfy` | dashed line, open arrow at the requirement `R` |
| `verify R` | `verify` | dashed line, open arrow at the requirement `R` |
| `dependency from A to B` | `dependency` | dashed line, open arrow at `B` |

`contain` is derived from `ownerId`; the others come from relationships.
`negated` satisfy edges are drawn with a strike-through marker later; for v0.2
they are rendered like satisfy but labelled `not`.

### 4.2 IBD view (`src/views/ibd.ts`)

**Context.** v0.2 renders the interconnection described anywhere in the model:
every `part` usage becomes a node, each carrying its own ports. (Selecting a
single IBD context is deferred.)

**Nodes** — every `part` usage (owned by a definition, another usage, or a
package). stereotype `part`. `ports` = names of its `port` children. referenced
`part-def`/`part` targets that appear only as endpoints are added as nodes too.

**Edges** — for each `connect` / `bind` relationship, resolve each endpoint
feature chain to `(partId, portName)`:

```
resolveEndpoint(chain):
  segments = chain.split('.')
  find the longest prefix that names a `part` element -> partId
  portName = the next segment after that prefix (or the last segment)
  if no prefix resolves -> (unresolved:chain, last segment)
```

The edge is emitted between the two owning part nodes, carrying
`sourcePort` / `targetPort` (port names). Connector styling: `connect` solid,
`interface` dashed, `bind` dotted.

`ViewEdge` gains optional `sourcePort` / `targetPort`; `ViewEdgeKind` gains
`connect` | `bind`.

### 4.3 View types

```ts
export type ViewName = 'bdd' | 'requirement' | 'ibd';
export type ViewEdgeKind =
  | 'specialization' | 'composition' | 'reference' | 'subset' | 'redefine'
  | 'dependency' | 'contain' | 'satisfy' | 'verify'
  | 'connect' | 'interface' | 'bind';

export interface ViewEdge {
  id: string;
  kind: ViewEdgeKind;
  source: string;
  target: string;
  label?: string;
  sourcePort?: string;
  targetPort?: string;
}
```

## 5. Layout

`src/layout/` gains a port-aware IBD layout:

- `SceneNode` gains `portAnchors?: { name: string; x: number; y: number }[]`
  (absolute positions).
- `SceneEdge` gains `sourcePort?: string; targetPort?: string`.
- `dagreLayout(view)` already positions nodes; a new `ibdLayout(view)`:
  1. runs the same dagre pass (rankdir `LR`);
  2. computes port anchors on each node's left/right borders: ports that are
     edge sources go on the right, edge targets on the left; distribute
     vertically; a port used both ways stays on the right;
  3. for a connector edge with resolved ports, sets
     `points = [sourceAnchor, targetAnchor]`; otherwise keeps dagre routing.

`BDD` and `requirement` keep the plain dagre layout (`rankdir: 'TB'`); the
layout dispatcher picks `ibdLayout` for IBD.

## 6. Render

`src/render/shapes.ts` draws ports from `node.portAnchors` when present (else the
existing fixed border positions), and `src/render/notation.ts` snaps an edge's
first/last point to the named port anchors when `sourcePort`/`targetPort` are
set. Connector line styles: `connect` solid, `interface` dashed, `bind` dotted.

New markers: `s2m-arrow` is reused; requirement `satisfy`/`verify` use dashed
edges. No new marker files.

## 7. Entry points

- Library API: `renderSvg(source, { view })` already accepts `view`; extend the
  union to `'bdd' | 'requirement' | 'ibd'`.
- CLI: `--view requirement` and `--view ibd` become valid.
