# Design: v0.3 — State machine and Activity/Swimlane views

English only.

## Status

Approved for implementation planning. Builds on v0.2. Reuses the existing
pipeline; adds parser constructs, two views, swimlane groups, and node shapes.

## 1. Scope

1. **State machine view** — `state def` / `state` usages, nesting, `entry`/`do`/
   `exit`, transitions, initial/final pseudo-states.
2. **Activity / Swimlane view** — `action def` / `action` usages, successions,
   object flows, control nodes, and `perform`-derived swimlanes.

### Out of scope

- Full trigger algebra (time/change triggers are captured as raw text only).
- `exhibit`, `parallel` regions beyond a flag, conjugated ports.
- Structured control (`if`/`while`/`for`/`loop` bodies); only their *references*
  appear as nodes via successions.
- Simulation semantics.

## 2. Parser additions

Verified against the SysML v2 textual BNF and validation models.

### 2.1 State machines

```sysml
state def VehicleStates { }              // definition (black box or with body)
state off;                               // usage, nested in a state/part body
state on : PowerState {                  // usage with a type
    entry action selfTest;               // entry / do / exit (raw action text)
    do providePower;
    exit applyBrake;
    state nested;                        // nested state
}
state running parallel { state a; state b; }   // parallel regions (flag)

transition 'off-starting' first off accept StartSignal if brakeDepressed do startEngine then starting;
transition first idle then off;          // unnamed transition
first idle then off;                     // anonymous (source = first operand)
then off;                                // target shorthand (source = previous state)
```

- `entry` / `do` / `exit` statements become child elements of kind `action`
  whose `name` is the keyword and whose `typeRef` holds the raw action text.
- A `transition` (or anonymous `first … then …`) becomes a relationship of kind
  `transition`, `sourceRef = <first operand>`, `targetRef = <then operand>`, and
  `label` = the normalized `accept … if … do …` text.
- **Initial pseudo-state**: a transition whose source operand is `initial` or
  `start`. **Final pseudo-state**: a target operand of `done` or `terminate`.
  These names are conventions, not keywords.
- `parallel` after a state name sets `Element.isParallel`.

### 2.2 Activities

```sysml
action def ProvidePower { in fuel : Fuel; out torque : Torque; }
action generate : GenerateTorque { }
action amplify : AmplifyTorque;
action monitor;

first start;                             // initial node + control flow
first engineStarted then 'generate torque';
first start then continue;
then validate;                           // succession from the previous node
validate then act;                       // binary succession
flow from focus.image to shoot.image;    // object flow
flow of Torque from generate to amplify;
then decide;                             // control nodes are ordinary references
decide;
fork; join; merge;
accept signal; send new Msg() to target; assign x := 0; terminate;
```

- `action def` / `action` usages (with `in`/`out` parameters captured as rows).
- `first <ref>;` → succession from an implicit `start` node to `<ref>`.
- `<a> then <b>;` / `first <a> then <b>;` → succession `a → b`.
- `then <b>;` → succession from the previous node named in the body to `<b>`.
- `flow [of <payload>] from <a> to <b>;` → relationship kind `flow`
  (`label` = payload).
- `perform [action] <ref>;` → relationship kind `perform`, source = enclosing
  element, target = `<ref>` (used for swimlanes, section 4.3).
- `accept` / `send` / `assign` / `terminate` statements are recorded as
  relationships carrying raw text in `label` from the current node (best effort;
  the raw text is preserved so the view can show it).

### 2.3 Lexical

- `parallel`, `first`, `then`, `entry`, `do`, `exit`, `accept`, `send`, `assign`,
  `terminate`, `flow`, `perform`, `action`, `state`, `transition` are handled as
  keywords by the parser; no tokenizer change is required.

## 3. Model additions

```ts
export type ElementKind =
  | ...existing...
  | 'state-def' | 'state'
  | 'action-def' | 'action'
  | 'control'            // decide / merge / fork / join / start / done nodes
  | 'unresolved';

export type RelationshipKind =
  | ...existing...
  | 'transition' | 'succession' | 'flow' | 'perform';

export interface Relationship {
  // ...existing...
  label?: string;        // transition trigger/guard/effect, flow payload, raw statement
}
```

`Element.isParallel?: boolean`.

`validate` resolves `transition` / `succession` / `flow` endpoints with the
existing qualified/simple-name rules. The special operands `initial` / `start`
(source) and `done` / `terminate` (target) are **not** resolved to placeholders;
the views handle them as pseudo-states. `control` elements (`decide`, `merge`,
`fork`, `join`) are created on demand from succession/flows that reference an
unknown name.

## 4. Views

`ViewName = 'bdd' | 'requirement' | 'ibd' | 'statemachine' | 'activity'`.

### 4.1 State machine (`src/views/statemachine.ts`)

- **Nodes**: `state-def` and `state` elements; nested states included; a
  `«initial»` node for each `initial`/`start` transition source; a `«final»`
  node for each `done`/`terminate` target.
- **Rows**: `entry` / `do` / `exit` children (`entry: <text>`), plus nested state
  names.
- **Edges**: transitions (`source → target`) with the `label` (trigger/guard/
  effect). Self-transitions allowed.

### 4.2 Activity (`src/views/activity.ts`)

- **Nodes**: `action-def` and `action` elements, `control` nodes, and the
  implicit `start` node.
- **Rows**: `in`/`out` parameters.
- **Edges**: `succession` (solid, open arrow), `flow` (dashed, labelled with the
  payload).
- **Swimlanes**: if any `perform` relationships exist, group actions by the part
  that performs them (section 4.3); otherwise one flat lane.

### 4.3 Swimlanes from `perform`

A `perform <ref>;` inside a `part` (definition or usage) means that part performs
`<ref>`. The activity view groups each referenced action under its performer.
The performer part becomes a **group** (swimlane) labelled with the part name;
actions performed by no part belong to a default group. Overlapping performers
are resolved by first match, with later performers ignored (documented).

## 5. Groups in layout and render

```ts
// layout/types.ts
export interface SceneGroup { id: string; label: string; x: number; y: number; width: number; height: number }
export interface Scene { nodes: SceneNode[]; edges: SceneEdge[]; groups?: SceneGroup[]; width: number; height: number }
```

`views/types.ts` gains `ViewGroup { id: string; label: string; members: string[] }`
and `ViewDescription.groups?: ViewGroup[]`.

Layout uses dagre compound graphs: each group is a cluster node (`setParent`),
so dagre computes the cluster bounds. Render draws a labelled rounded rectangle
behind each group's nodes.

## 6. Render

- New node shapes by stereotype:
  - `initial` → a small filled circle.
  - `final` → a circle with an inner filled circle (bullseye).
  - `decision` / `merge` → a diamond; `fork` / `join` → a thick bar.
- Transition labels reuse the edge label rendering.
- Group rectangles are drawn first (behind nodes), with a light header strip.

## 7. Entry points

- CLI `--view statemachine` and `--view activity`.
- Library API `renderSvg(source, { view })` accepts the new names.
