# Design: v1.0 — Semantic validation

English only. Builds on v0.9.

## Status

Approved for implementation planning.

## 1. Scope

Add model-level semantic checks on top of the existing resolution pass, reported
as positioned diagnostics. These deepen the Language Server's value (better
squiggles) without changing the pipeline.

Checks:

1. **Type-kind mismatch** — a usage typed by a definition of an incompatible
   kind (e.g. a `part` typed by a `port def`).
2. **Satisfy / verify roles** — a `satisfy` source should be a requirement and its
   target a usage; a `verify` target should be a requirement.
3. **Connector endpoints** — a `connect` / `interface` endpoint should name a port
   of the owning part (own or inherited from its type).
4. **Multiplicity** — a numeric range with lower > upper.
5. **Specialization cycle** — a definition that (transitively) specializes itself.

All checks are conservative: they only fire when the referenced element is
resolved, so models referencing an unbundled standard library stay quiet.

## 2. Diagnostics

| Code | Severity | Trigger |
| --- | --- | --- |
| `type-kind-mismatch` | warning | usage typed by an incompatible definition kind |
| `satisfy-source-not-requirement` | warning | `satisfy` source resolved to a non-requirement |
| `satisfy-target-is-requirement` | warning | `satisfy` target resolved to a requirement |
| `verify-target-not-requirement` | warning | `verify` target resolved to a non-requirement |
| `connect-endpoint-not-port` | warning | `connect` endpoint owner resolved but the named port is absent |
| `invalid-multiplicity` | error | numeric `lower > upper` |
| `specialization-cycle` | error | a definition specializes itself transitively |

## 3. Implementation

A new `src/core/model/semantic.ts` exporting `checkSemantics(model): void`, called
at the end of `validate()` (after references are resolved). It reads
`element.typeId`, `Relationship.sourceId/targetId`, and the specialization graph.

- **Expected type kinds** (usage → allowed definition kinds):

  | Usage | Allowed type kinds |
  | --- | --- |
  | `part` | `part-def`, `other` |
  | `item` | `item-def`, `part-def`, `other` |
  | `port` | `port-def`, `other` |
  | `attribute` | `attribute-def`, `enum-def`, `other` |
  | `action` | `action-def`, `other` |
  | `state` | `state-def`, `other` |
  | `requirement` | `requirement-def`, `other` |

  (`other` is allowed to avoid false positives on generic/KerML declarations and
  on unresolved library names.)

- **Ports of a part** (for connector endpoints): own `port` children plus the
  `port` children of `typeId` (recursively), mirroring the IBD view.

- **Specialization cycles**: DFS over `specialization` edges (sourceId → targetId),
  reporting one error per detected back-edge.

## 4. Testing

`test/semantic.spec.ts` covers every code: a part typed by a port def, a good and
bad `satisfy`/`verify`, a connector to a missing port and to an inherited port, an
inverted multiplicity, and a `:>` cycle. All 160 existing tests stay green; a
couple of fixtures may gain warnings but must keep zero *errors*.
